# 根因排查与回归

处理缺陷、测试失败、构建和运行异常时，先定位故障，再选择改动。

1. 阅读完整错误、堆栈和最近相关变更。记录预期、实际、触发条件及是否稳定复现。
2. 找到最小复现路径。多组件问题沿输入、配置传递、输出和持久化边界收集必要证据，不输出凭据或批量敏感数据。
3. 对照正常路径提出可证伪的假设，每次只改变足以区分假设的条件。区分业务错误、环境故障、外部依赖和测试自身问题。
4. 确认原因后，用能区分正确与错误行为的回归测试保护修复，再进入红—绿—重构。若原因是环境配置，使用对应诊断或校验，不强写无关业务测试。
5. 验证原始复现路径与受影响的邻近行为。反复失败而没有新证据时，扩大诊断或重新检查架构假设，不堆叠猜测性补丁。

例如订单取消偶发扣两次库存：先确定是两个独立请求、同一请求重试、消息重复消费还是显示重复；检查库存写入边界和请求标识。业务尚未约定重试语义时，记录待决问题；不能仅禁用按钮就宣称后端重复写入已修复。

暂时无法复现时交付已找到的事实、排除条件和下一步所需证据，不把可能原因写成确认根因。临时缓解若在授权范围内，说明它缓解什么、残留什么以及如何验证。
